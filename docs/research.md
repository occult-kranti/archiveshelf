# Research and engineering decisions

## Executive summary

The reference product’s public workflow is not fundamentally a video downloader. Its public site describes channel and bulk-list imports, an organized transcript archive, source comparison, saved extracts, and text export. The supplied application screenshot adds a conventional library sidebar and a video detail area with Summary, Transcript, Generate, and Chat tabs. ArchiveShelf preserves the useful source-first loop—import, normalize, search, inspect, and export—but does not reproduce private account systems, credits, branding, or proprietary implementation details ([BeyondTube](https://beyondtube.pro/)). Audio extraction is an explicit extension requested for this project, and the UI intentionally omits AI buttons rather than presenting unimplemented generation or chat as real features.

The strongest implementation base is a small adapter around maintained extraction and transcription components, not a new scraping stack. `yt-dlp` supplies channel/playlist handling, caption options, post-processing, retries, output templates, and archive-related behavior, while FFmpeg performs the actual media conversion ([yt-dlp](https://github.com/yt-dlp/yt-dlp)). A separate Python worker gives the CLI and web server exactly the same behavior, and JSON events plus per-item manifests create a reliable contract between them. The web layer adds authentication, owner-scoped metadata, object-backed audio, and on-demand text/ZIP downloads. This keeps the core useful on its own and avoids turning a research tool into a heavyweight media server.

## 1. Reference workflow and scope

BeyondTube’s public landing page describes three broad steps: import videos or channels, analyze and structure the resulting knowledge, and create outputs grounded in that dataset. It also advertises monitoring and bulk-ready archives. Those observations support a data model centered on sources, transcripts, and processing history rather than a simple one-off download form ([BeyondTube](https://beyondtube.pro/)). ArchiveShelf therefore includes a library, full-text search over imported transcript text, channel filtering, job progress, partial-failure reporting, source details, and per-video or per-job exports. The interface follows the supplied screenshot’s split navigation/detail pattern but uses an original name, icon, palette implementation, and component structure.

The requested “workarounds” need a firm boundary. YouTube’s terms restrict unauthorized downloading, automated collection, and circumvention, and the same rules apply regardless of whether a project is labelled academic research ([YouTube Terms](https://www.youtube.com/static?template=terms)). The implementation consequently has no proxy rotation, browser-cookie harvesting, signature patching, private-video access, or anti-bot evasion. Restricted, private, unavailable, and rate-limited items become structured failures and the batch continues. Users must affirm authorization before a web or CLI job starts. Live testing used a CC0 external clip and original local fixtures; the screenshot’s third-party channels were not bulk-downloaded, and ambiguous names were left unresolved rather than mapped to guessed URLs.

## 2. Engine and library comparison

The evaluated choices solve different layers of the problem. `youtube-transcript-api` offers a small Python API and existing TXT, JSON, VTT, SRT, and CSV formatters, making it attractive when only YouTube caption text is needed ([youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api)). It is not a complete audio archiver, however, and its own documentation discusses blocked-request handling. ArchiveShelf uses `yt-dlp` for the common source path and its own normalized serializer so direct media, captions, and local Whisper segments all produce the same five output formats. This avoids maintaining two incompatible transcript schemas. No ban-evasion options from any library are enabled.

Larger archive projects validate several useful patterns but carry unnecessary operational weight for this request. Tube Archivist combines a web interface, indexing, and a substantial media archive stack, while `ytdl-sub` emphasizes repeatable YAML-driven subscriptions and metadata for media servers ([Tube Archivist](https://github.com/tubearchivist/tubearchivist), [ytdl-sub](https://github.com/jmbannon/ytdl-sub)). ArchiveShelf instead borrows the ideas of per-source manifests, idempotent re-runs, and structured directories without importing those codebases. The resulting directory layout is `Channel / Year / Title [id]`, containing `audio.*`, `transcript.{txt,md,json,srt,vtt}`, `metadata.json`, and `manifest.json`. A batch-level `index.jsonl` makes ingestion and recovery deterministic.

| Option | Strength | Limit for this project | Decision |
|---|---|---|---|
| [`yt-dlp`](https://github.com/yt-dlp/yt-dlp) | Broad source support, captions, metadata, playlists, FFmpeg post-processing | Direct CLI output alone does not provide a user library or web jobs | Primary source adapter |
| [`youtube-transcript-api`](https://github.com/jdepoix/youtube-transcript-api) | Focused caption API and mature formatters | Captions only; blocked requests must not become an evasion workflow | Useful reference/fallback candidate, not required at runtime |
| [`openai/whisper`](https://github.com/openai/whisper) | Reference speech-recognition implementation with timed segments and an official model distribution | PyTorch and numerical native dependencies | **Default backend; verified end to end** |
| [`faster-whisper`](https://github.com/SYSTRAN/faster-whisper) | CPU INT8 and GPU transcription with timed segments | Native dependencies and a separate Hugging Face model download | Alternative backend; model download unverified |
| [`Tube Archivist`](https://github.com/tubearchivist/tubearchivist) | Full archive product and searchable library patterns | Much broader infrastructure than a simple research tool | Pattern research only |
| Direct FFmpeg | Minimal, deterministic audio conversion | No channel enumeration, caption discovery, or normalized metadata | Used inside the worker and as a comparison spike |

## 3. Transcription and export architecture

Both local speech backends were evaluated rather than assuming one hosting path would work. OpenAI Whisper’s code and model weights are MIT-licensed, and its official tiny checkpoint downloaded successfully and matched the published SHA-256 ([OpenAI Whisper](https://github.com/openai/whisper)). It is now the default backend after passing the complete worker test on original speech. `faster-whisper` remains an alternative with CPU INT8, GPU options, and batched inference, but its Hugging Face model download timed out and is not represented as verified ([faster-whisper](https://github.com/SYSTRAN/faster-whisper)). Captions remain the first choice because they avoid transcription compute and preserve source timing; either speech backend runs only when captions are missing and the user has opted in.

All transcript origins converge on a common `start`, `end`, and `text` segment model. From that model the worker writes readable paragraphs, a Markdown source header, structured JSON, SRT, and WebVTT. The web database stores the plain text and raw JSON segments for search and future export, while audio bytes are uploaded through the platform’s server-only storage SDK. Persistent ZIP uploads repeatedly failed during live verification, so the final architecture generates ZIPs on demand for the authenticated owner. This is not a storage-review workaround: no document is being hidden or relabelled. It simply removes redundant persistent files and generates a response from already verified audio and structured transcript data.

## 4. Reliability, security, and test findings

Reliability is built around bounded concurrency, isolated per-video failures, explicit status, and resumable manifests. The worker uses one to three threads, never an unbounded swarm, because every item may create multiple source requests and an FFmpeg process. Retryable object-storage errors receive a short bounded backoff; non-retryable failures surface immediately. Cancellation terminates the worker’s process group, and partial means exactly what it says: at least one requested artifact is missing. The stress suite injects a 404 and confirms that other items still finish. Its current benchmark for the same three local files is 5.767 seconds with one worker and 2.592 seconds with three, with zero retained video files in either mode. These are local measurements, not claims about remote-service throughput.

Security review covers authentication, ownership checks, URL policy, dependency advisories, and secret hygiene. Web downloads check the session and resource owner, private or local destinations are blocked by default, and the private-URL switch exists only for local fixtures. The production bundle cold-starts without `node_modules`, and its worker plus pure-Python runtime dependencies are packaged deliberately. Production dependencies report zero known vulnerabilities after compatible updates; no force upgrade was used. The repository excludes `.env`, `.python`, `dist`, `node_modules`, exports, archives, media, and test artifacts. Detailed evidence, including the failed storage-ZIP path that led to the on-demand design, is recorded in [TESTING.md](TESTING.md).
